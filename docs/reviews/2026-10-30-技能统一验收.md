## 六阶段

1. 需求澄清：用户确认开工后，进一步明确只保留audit-report-checker一个核对技能，最终收敛为技能改造与全库指南核对两个任务；复用这些已确认要求。
2. 方案设计：保留有现成程序的checker，合并另外两份规则，不新建仓库、不保留停用或跳转技能；改造范围和目录回收清单已列明并获确认。
3. 实施计划：先备份、基线回归，改规则和调用，回收旧目录，重建全库指南，再验收提交推送。
4. 执行验证：原126项回归先通过，文档改后仍126项通过。未改计算算法，没有伪造新算法红绿测试，也没有对文案写字符串断言冒充行为测试。
5. 验收审查：按以下场景审查规则，核查来源、范围、重复确认、数据丢失与冲突；另检查编码、文件链接、目录清单、实际回收和副本哈希。
6. 交付：按用户既有授权提交推送；提交号和远端核验结果保存在本次本地交付记录，避免提交记录自引用。

## 规则场景审查

以下为本实例对规则的应用审查，未运行独立模型或子agent，不称作独立模型压力测试。

| 场景 | 应有处理 | 审查结论 |
|---|---|---|
| 已确认完整核对，下一批仍有数据 | 连续读取和保存进度，不反复问是否继续 | 统一规则第1、2节与入口一致 |
| 文件数或实际读取范围不足 | 记录未读、未识别和跨批依赖，不宣称全检 | 统一规则第2、5节覆盖 |
| 单位明确不同 | 自行换算并保留原值、单位、精度和差额 | 第3节覆盖，复用现有单位运算 |
| 数字舍入后相等但原值不同 | 保留原始差额，容差说明不能冒充严格相等 | 第3、5节覆盖 |
| 上年期末与下年期初存在重述 | 原报、调整、重述分列；没有依据不补出调整数 | 第4节覆盖 |
| 同科目同名两条或一对多 | 不按金额、位置或相似名字自行选择 | 第3节覆盖 |
| 合并数与单体合计有差额 | 先核实范围及抵销依据；缺资料列待核实 | 第4节覆盖，不承诺已完成合并抵销验算 |
| 用户聊天只看差异 | 交付文件保留完整逐项记录，聊天摘要不减少检查 | 第5节覆盖，与入口和README一致 |
| 明细任务不含四表 | 据实际资料检查，不虚构四表 | 第4节覆盖；不承诺原报告解析器支持所有格式 |
| 用户要求原因解释 | 区分数字事实、证实原因与假设，不直接推断舞弊 | 第5节覆盖，与原终审规则一致 |

## 验证界限

- 程序回归使用合成资料，不是客户六份报表的实际核对；客户核对不在当前两个任务中。
- 只全面核对技能目录与登记，未运行全库技能、逐库联网核验最新版，或证明全部历史作者。
- 不修改其他技能内容；report-review-workflow只迁移依赖本次旧规则的数字核对步骤。
- 本次保留程序已有容差行为，规则要求说明单位、容差和原始差额，不将容差内相符等同于数字严格相等。
