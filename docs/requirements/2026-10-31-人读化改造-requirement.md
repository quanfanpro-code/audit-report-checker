# 需求文档：复核报告人读化改造

- 日期：2026-10-31
- 状态：已确认（用户审阅需求书后批准推进）
- 依据：用户需求书《审计报告复核技能-人读化改造-需求书.md》（2026-10-31）

## 一、背景与问题

技能 audit-report-checker 复核真实报告后，交付物存在两类毛病：

1. **输出不是给人看的。** 人读页出现内部编号、底稿黑话（「现补表」「CFS 主表」「r5代码34」「表60」）、浮点碎尾数（11449812.430000007）、竖线数据流、无效定位（「第1–75行」「对应文字片段」）、甩锅式建议（「请项目组确认」）。读者要在一堆信息里自己拼结论。
2. **结论本身出过错。** 程序把 Excel 里隐藏的空白工作表「现补表」当正式报表核对，拿隐藏表里的 0 与主表比较，报出不存在的「致命问题」；真正数字在 Word 附注里且与主表一致。旧版导出把 AI 工作底稿原文直接搬进「凭什么说错」。

现状证据（2026-10-31 对真实产出《复核结果_人读版.xlsx / .md》的独立评价）：
- 假错误仍列致命问题第一条；
- 用户点名批评过的底稿语言原样保留；
- 黑话、碎尾数、无效定位、甩锅建议均在；
- 三层结构（概览/明细/隐藏技术页）与机器信息隔离这两点已做到。

## 二、用户与使用场景

- **读者**：项目组复核人员、报告使用者。不懂程序，需要在一分钟内判断「严重吗、在哪、错什么、差多少、凭什么说错、怎么改」。
- **场景**：复核完成后打开 Excel 或 Markdown 报告，先看完结论和最要命的问题，再逐条处理明细；必要时按定位回到原始文件核对。
- **技术追溯**（罕见）：需要对象 ID、完整路径等时，展开默认隐藏的技术留痕页。

## 三、功能范围

### 3.1 每条问题七个栏目（核心）

固定栏目及标准（用户认可范本见需求书附录）：

1. **问题（一句话）**：标题即结论，说清「什么和什么对不上、差多少」。禁止内部编号进标题。
2. **严重程度**：致命 / 重要 / 细节。
3. **错在哪**：三段定位——哪个文件；具体位置（哪一节、哪几行、表名）；跟什么对照。禁止大范围区间充数。
4. **核对了什么**：一句大白话说清核对规则。
5. **差多少**：有金额差异写「明细加总/合计/差额」；无不适用。金额给人读格式（千分位、两位小数，大数可用万元），禁止浮点碎尾、禁止竖线数据流。
6. **凭什么说错**：固定三句——核对方式、关键差异、判断结论。只写人话。
7. **怎么改**：具体、可执行、有完成标志。禁止「请项目组确认」式甩锅。

### 3.2 三层结构（保持）

问题概览（结论先行＋计数＋最要命清单）→ 问题明细（七栏目）→ 技术留痕（默认隐藏，机器信息全在此）。

### 3.3 隐藏内容规则（事故教训，写死）

- 只复核打开文件后肉眼可见内容：隐藏工作表、隐藏行、隐藏列一律不读、不核对、不参与比较。
- 发现隐藏内容只登记一句提醒（范式见需求书需求 3），不报错、不算差异。
- 旧复核结果里混入的隐藏来源数据：导出时剔除，不得进问题清单。
- **假错误确认后必须从问题清单撤销**，可在「已排除误报」区留一行说明。

### 3.4 语言与数字规范

- 全文自然中文；内部叫法（现补表、CFS、表N、rN代码、未审、附注N、内部关系编号）一律翻译或只留技术层。
- 报告文字为读者重写，禁止把 AI 工作底稿原文清洗粘贴。
- 一条问题一个主题；归并同类后用人话概括影响面。
- 严重程度口径：致命=已确认且出报前必改；重要=需核实或补资料；细节=不妨碍出报应改进。程序不得仅凭状态自动升级。
- 标题与内容不得自相矛盾（「不受影响」不得列为重要问题）。
- 修改版报告只留正文，不夹带机器标记。

### 3.5 流程（已有约定，纳入验收）

- 先文档后动手；测试先行（先失败后通过）；完整回归全绿。
- 不回退已验收的流程精简成果（脚本固定复用、按需读取、重复读取已合并）。
- 用真实资料生成人读版报告作为最终验收。

## 四、明确不做的内容

- 不重做复核算法与判定逻辑；只改「取数时跳过隐藏内容」和「展示层」。
- 不改其他技能；不清理、不删除用户原始资料（含空白「现补表」，只提醒）。
- 未获指令不提交、不推送版本库（本次用户已授权完成即提交推送，见约束）。

## 五、约束与风险

- **约束**：修改前备份到项目外 BackUp 目录；测试文件与实现同步；README 更新记录认真写。
- **风险 1**：results.json 等旧结果含隐藏来源数据且无来源标记，只能按 table_id → 提取表 → 源表 sheet 状态链路识别，识别不到的兜底策略需在设计中明确。
- **风险 2**：「凭什么说错」三句话结构依赖结构化差异数据（calculations）；对无差异数据的「通读发现」类问题，只能基于 review 文本改写，改写质量需人工可读性测试兜底。
- **风险 3**：真实源文件 04附注 于 2026-10-31 10:34 被重新保存（与 results.json 记录的指纹不一致，正文经比对无实质变化）。导出保护会拦截。验收报告的生成方式需按「来源变化」处理（见待确认项的处理决定）。

## 六、验收标准

1. 真实报告无「现补表不一致」假致命问题；隐藏内容只出现在提醒区，措辞用需求书范式。
2. 隐藏的工作表、行、列均不参与复核，有测试证明。
3. 人读页检索不到：现补表、CFS、r5代码、表8/表17/表50/表54/表60、对象 ID、完整路径。
4. 人读页检索不到浮点碎尾和竖线数据流。
5. 每条问题七栏目齐全，逐条通过「一分钟测试」。
6. 「错在哪」可定位到具体一节/几行，无「第1–75行」「对应文字片段」。
7. 「怎么改」有具体动作和完成标志，无甩锅句。
8. 概览第一屏含出报结论＋计数＋最要命清单。
9. 技术层默认隐藏且完整保留原始记录。
10. 完整自动测试全绿；真实报告由真实资料新生成。
