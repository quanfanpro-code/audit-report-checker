# audit-report-checker 人类可读复核报告需求

## 背景与问题

当前复核结果按程序字段和执行过程组织。旧版 Excel 使用七张分类表，可见内容包含对象 ID、完整技术路径、表格 ID、原始区间、来源指纹和 JSON 路径；Markdown 展开大量未执行记录及全部计算过程。使用者需要自行筛选、合并和判断，无法直接回答“严重吗、在哪里、怎么改”。

本次改造以使用者的阅读任务为中心，重新组织 Excel、Markdown 和修改版报告的输出规则，并用已有真实复核结果生成新版报告验收。

## 用户与使用场景

- 复核人员：需要迅速判断报告能否出报、优先处理哪些问题。
- 报告编制人：需要知道错误内容、原始位置、判定原因和具体修改方法。
- 技术追溯人员：只在需要时查看内部编号、完整路径、原始区间、指纹和其他机器字段。

## 功能范围

1. 在技能中建立适用于全部交付物的“输出组织总则”。
2. 将 Excel 和 Markdown 重排为三层：
   - 问题概览：出报风险、致命/重要/细节数量、最优先问题。
   - 问题明细：每项完整展示“问题、错在哪、原文、核对结果、凭什么说错、怎么改”。
   - 技术留痕：Excel 独立 Sheet，默认隐藏；Markdown 不混入机器信息，完整机器数据继续由 results.json 保存。
3. 可见位置使用文件名、真实工作表或章节及从 1 开始的日常行号；可见金额采用易读格式，原始精度保留在技术留痕。
4. 同类重复的未执行记录先归并，通过、不适用和已排除误报不得淹没待处理问题。
5. 复核回填支持人话标题、原文、修改建议和业务严重程度；历史结果缺少这些字段时，从已有依据和原始表格生成可读内容，不虚构判断。
6. 修改版报告只保留修改后的正文，不插入内部批注、任务标识或工具标记。
7. 同步更新 SKILL.md、README、CONTEXT 和相关测试，并保留原有来源校验、覆盖检查和终审要求。

## 严重程度口径

- 致命：已经确认错误，且出报前必须修正，例如金额不一致、应填内容整项缺失。
- 重要：尚不能直接认定错误，但必须由项目组核实或补资料，例如占位编号、异常日期、未完成的必要核对。
- 细节：不妨碍出报，但应修改或改进的问题，例如文字、格式和规范性瑕疵。
- 复核人员可按具体业务影响调整等级，程序不得只凭状态机械拔高或降低严重程度。历史结果缺少人工等级时，按上述口径作展示映射，不把它当作新的审计判断。

## 明确不做的内容

- 不修改原始报告、原始数据或既有复核结论。
- 不把本次工作扩展到 report-review-workflow 或其他技能。
- 不重新阅读已停止使用的历史会话压缩包；优先直接使用已有 results.json 和提取结果。
- 不在信息足够时重新执行整套复核。
- 不默认生成或改写客户正式报告正文，只规定以后生成修改版报告时的清洁要求。
- 未取得明确指令前，不提交、不推送、不创建 PR。

## 约束与风险

- 状态表示复核结论，严重程度表示出报影响，两者不得混为一谈。
- 历史结果中的部分依据含内部编号或 JSON 片段，可见报告必须清理，但技术留痕不得丢失原始信息。
- 同源问题可能对应多条复核记录，展示计数不得冒充独立错误数；重复记录应归并或说明关联。
- 位置、原文和修改建议必须来自已有数据或明确 fallback，不得编造页码、引文、业务原因或处理结论。
- 修改任何已有文件前先备份并校验，原始资料始终只读。

## 验收标准

1. Excel 可见页只有“问题概览”和“问题明细”，“技术留痕”独立且默认隐藏；Markdown 采用相同人读逻辑。
2. 首次阅读者无需跨表拼凑，即可看到严重程度、错误内容、原始位置、原文、核对结果、判定原因和修改建议。
3. 可见页面不出现对象 ID、来源指纹、完整技术路径、表格 ID、原始区间、JSON 路径或工具日志；技术留痕完整保留这些信息。
4. 致命、重要、细节按已确认口径展示，人工业务等级优先于程序状态。
5. 大量同类未执行记录被归并，主要错误和异常位于最前；修改版报告不含机器标记。
6. 全部自动测试通过，覆盖正常、边界和错误路径；旧测试中针对七张机器表的断言同步更新。
7. 使用已有真实复核结果生成新版 Excel 和 Markdown，读回确认中文、金额、位置、统计、隐藏状态和源文件哈希正常。
